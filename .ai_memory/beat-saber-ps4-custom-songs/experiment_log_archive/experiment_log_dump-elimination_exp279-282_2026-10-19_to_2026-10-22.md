### Experiment 280c: user's Deploy-Plugin smoke test failed with "❌ Not Found" — the round-3 stale-process lesson: version endpoints must report the RUNNING code (captured at import), not a request-time file read (2026-10-19)
- **User:** quick smoke test of the new Deploy Plugin button → "❌ Not Found".
- **Diagnosis:** the running 8765 server HAD the game-data endpoints (an Exp-280-era process) but NOT the plugin endpoint — yet its ping reported webapp 0.6.15. Root cause: the ping read the VERSION file FROM DISK at every request, so a stale process reports the NEW version while serving OLD code — and that ALSO defeats the launcher's staleness check (ping == current file → "current" → reuse the stale server). The exact same stale-process class as 278g, now with a version-lie twist that defeated the very detection built to catch it.
- **Fix (folded into the unreleased 0.6.15):** server.py captures all three versions at import (`_capture_code_versions()` → `_CODE_WEBAPP_VERSION`/`_CODE_PIPELINE_VERSION`/`_CODE_PLUGIN_VERSION`); the ping reports those. A stale process now honestly reports its own version → the launcher flags it STALE → stop-and-restart default takes over. 3 regression tests (the pin: mutate the version file after import → the ping values don't change; the capture constants exist; the class-detection note).
- **Also:** the stale process killed + a fresh current server started + verified (ping 0.6.15 AND the deploy-plugin route registered); the simulated release rebuilt with the fix + boot-verified (ping: 0.6.15/0.5364/bundled + the route present).
