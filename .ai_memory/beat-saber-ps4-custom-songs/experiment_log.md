# Experiment Log: Beat Saber PS4 Custom Song Support — M10 Song Previews

**Feature:** Redirect the song-menu preview to the custom song's own audio.
When the player highlights a custom song in the song menu, the PS4 currently
plays the STOCK song's 10s preview clip — confusing. We patch each pack
bundle's per-song `BeatmapLevelSO._previewAudioClip` (FSB5) with a preview cut
from the custom song's own audio, honoring the mapper's `_previewStartTime`
from Info.dat. Plan: `.agent/plans/song-previews.md`.
**Started:** 2026-10-09 (Exp 268)
**System:** PS4 FW 9.00, GoldHEN 2.3 / 2.4b16.2
**Feature flag:** `enable_song_previews` (new, defaults false when absent)
**Archive:** Exps 244-267 (M9 Web App) → `experiment_log_archive/experiment_log_web-app-interface_exp244-267_2026-09-28_to_2026-10-09.md`

### Experiment 268: M10 kickoff — song-preview architecture research-verified; plan written (2026-10-09)
- **User:** confirmed the deployed Pages site looks good (M9 done); next feature: SONG PREVIEWS — the menu currently plays the stock song's preview when a custom song is highlighted; choose an appropriate couple of seconds from each custom song and redirect preview playback. New feature flag matching the existing naming; detailed plan in .agent/plans BEFORE work; keep the plan updated.
- **Research (all verified against real bytes, not assumptions):**
  - **Runtime chain (dump.cs):** song-menu selection → `LevelCollectionViewController.SongPlayerCrossfadeToLevelAsync` → `BeatmapLevelSO.get_songPreviewAudioClip()` (RVA 0x988E60, returns `_previewAudioClip` PPtr @ 0x48) → `SongPreviewPlayer.CrossfadeTo(clip, volume, startTime, duration)`. BeatmapLevelSO = the SAME class we already patch for mode selectors.
  - **Storage (verified across all 5 replaced packs — britney 11/11, camellia 6/6, lizzo 9/9, RS 11/11, billie 10/10):** every `_previewAudioClip` is a LOCAL PPtr (m_FileID=0) to an AudioClip in the same pack-bundle CAB; the N clips are concatenated in the bundle's inner `.resource` (e.g. lizzo: 9 clips in 5,066,944 B); every SO has `_previewStartTime=0.0`, `_previewDuration=10.0` — clips are PRE-CUT, so the SO floats never need touching; only the AudioClip's `m_Resource.m_Offset/m_Size` + header fields do.
  - **Codec:** stock previews = FSB5 **Vorbis mode 15** (encoder-BLOCKED per KB); our full-song clips = FSB5 **PCM16 mode 2** (hardware-proven fleet-wide) → reuse PCM16. 10s stereo 44.1k = 1,764,000 B/preview. `build_pcm16_fsb5()` already takes `clip_seconds`.
  - **Mapper intent:** 94/94 local sources carry a preview start (V2/V3 `_previewStartTime`; V4 `audio.previewStartTime`) — we honor the mapper's moment, not our own guess; heuristic fallback for absent fields.
  - **Flag mechanics — architectural insight:** previews ride INSIDE the patched pack bundle (same one as mode buttons) → `enable_song_previews` is a redirect-set switch like Exp 222's `enable_beatmap_mode_mapping`, and the flag matrix needs bundle VARIANTS (modes+previews / modes-only / previews-only / stock) selected at deploy time from features.json; redirects carry the variant name as VALUE.
  - **Machinery reuse:** `rebuild_bundle_file()` already re-emits the `.resource` node; appending new PCM16 blobs at the stream end + repointing only patched clips leaves every untouched clip's bytes/offsets intact. CRC + catalog handled by existing `crc_decompressed_stream`/`update_catalog_entry` (Exp 189 dataIndex shifting covers the size change).
- **Deliverables:** `.agent/plans/song-previews.md` (full plan: problem, findings, design incl. fade-in/out + loudness match, 4 phases, open questions); roadmap M10 section; experiment log rotated to M10 (M9 archived exp244-267); new session transcript.
- **Open questions for Phase 1 (hardware spike, lizzo 9 slots):** Q1 `m_CompressionFormat` value for PCM16 clip (mirror our proven custom-bundle value vs stock-PCM16 convention — hardware is the oracle); Q2 resource-append block handling; Q3 preview loudness vs stock (measure stock RMS as reference); Q4 mirror stock `m_LoadType=1` + defaults exactly.
- **Status:** ✅ research + plan complete. Next: Phase 1 spike — build the lizzo modes+previews variant, deploy, user listens in the song menu.

### Experiment 269c: previews confirmed working on hardware; batch optimization (skip-flag + per-pack dirty-check, pipeline 0.5359) (2026-10-09)
- **User:** re-ran the full lizzo batch to prove their process works; LAUNCHED THE GAME and checked the lizzo previews — all working across all custom songs; boot toast v0.8048 with 4/4 features ON. Three asks: (1) is lizzo hardcoded anywhere — previews must work for ANY pack/song (no hardcoding anywhere); (2) batch deploys regenerate previews for every pack each song — optimize with a --skip-song-preview-management parameter (applied to all-but-the-last batch command) + only regenerate previews for packs actually touched, leveraging pipeline data; (3) download + analyze the PS4 log to validate the boot.
- **PS4 log analysis (archived to .ai_memory/experiment_logs/v0.8048_song_previews_first_boot.txt, log cleared after):** the v0.8048 session (856 opens) shows everything expected — `song_previews=1` parsed from features.json; 53 redirects loaded (47 songs / 5 packs / 1 catalog, variant names in the e.g. line); all 5 packs' PREVIEW-VARIANT bundles served REDIRECTED (18 pack opens); catalog redirected; lizzo pack opened 5× (menu browse + per-song preview loads = the previews playing); 86 MoveNext metadata swaps; ZERO crash/error markers.
- **Hardcoding audit:** NONE — the entire preview path is data-driven: pack scope from the deployed redirects.json state (_resolve_deployed_packs), slot→pack mapping from beat_saber_song_ids.json (all 36 packs), custom-slot detection via song_metadata.json membership, audio from each slot's own deployed bundle. The user's batch already PROVED genericity: 46 previews across all 5 packs built with zero pack-specific code. Any new pack gets previews identically.
- **Optimization layer 1 — --skip-song-preview-management (CLI + batch auto-inject):** skips previews-variant BUILD management for a run (deploy of the existing variant still happens). batch_runner.py appends the flag to every batch command except the LAST (previews regenerate once at the end); honors a user-supplied flag on the last command with a printed NOTE. Threaded through --deploy-full's deploy_pack_bundle → deploy_pack_modes → _ensure_pack_mode_bundles and the deploy-only CLI paths. Documented in the CLI help + README flags section.
- **Optimization layer 2 — per-pack dirty-check (_previews_pack_dirty):** rebuild only when (a) variant file/manifest row missing, (b) modes base mtime newer than the row's previewsAt (valid: both local builds), (c) the custom-slot set changed (song added/cleared), or (d) any slot's input fingerprint changed — [bundle_md5, info_dat_md5] per slot (NO UnityPy parsing on the skip path; the audio AND the heuristic's embedded beatmaps both live inside the bundle the md5 covers; Info.dat md5 covers the mapper-start source). Clean-fleet skip pass measured: 23.3s (pure md5 reads) vs 152s rebuild-all — and profiling caught _repo_title_index reparsing ~100 repo Info.dats PER SLOT (46× waste = 42s) → now process-cached.
- **Docs:** README feature table gains Song Previews (✅ Working v0.5357+) + the new flag documented; changelog v0.5359. 843/843 tests (7 new: flag threading, 4 dirty-check legs, fingerprint shape, cache identity, runner injection); lint clean.
- **Status:** ✅ previews hardware-confirmed + optimized. Batch time for an N-song pack: N-1 preview passes eliminated + dirty-checking makes even the last pass cheap when nothing changed.

### Experiment 269e: CE-34878-0 crash after batch — RCA'd from the PS4 log + bytes; 3 defenses added; live PS4 repaired (pipeline 0.5361) (2026-10-10)
- **User:** lizzo batch succeeded and was MUCH faster (preview processing only at the last song — the optimizations visibly working), but booting Beat Saber crashed with CE-34878-0. Asked for log download + RCA + fix + defensive programming + unit tests for the new scenario.
- **Log analysis (archived v0.5360_preview_batch_crash.txt):** the crash session (3rd boot in the log) shows all 5 packs' variants served REDIRECTED, catalog redirected, lizzo opened at #267 in pass 1 — but pass 2 of the pack scan NEVER re-opened lizzo (healthy sessions open it 2-4×) and the log dies at RS's redirected open #571, mid pack-scan: the classic lazy-CRC-validation crash signature (Exp 180 family).
- **Byte-level RCA (the decisive forensics):** catalog-lizzo entry said crc 2,222,108,153; the deployed lizzo variant's ACTUAL crc = 1,065,772,882. SAME SIZE (22,656,896), DIFFERENT BYTES. Stream-diff localized the delta to EXACTLY one preview slice (EverybodysGay's) — two different valid builds of the same variant. The other 4 packs matched.
- **Root cause chain (two v0.5359 'optimizations' interacting):** (1) `deploy_pack_bundle` UPLOADED whatever variant existed locally (pass 1, built from the fresh BeatSaver re-downloads of batch song 1), then called `deploy_pack_modes` whose dirty-check saw the just-touched modes-bundle mtime → REBUILT the variant (pass 2 — bytes differ because song bundles had been rebuilt) → regenerated the catalog with pass-2's CRC → but my same-SIZE upload-skip blocked pass-2's corrective upload (same slot set = same size ALWAYS for preview variants) → PS4 kept pass-1's file with pass-2's catalog → Unity CRC validation fails lazily at the pack scan → CE-34878-0.
- **Fixes (3 layers):**
  1. **Sound upload-skip:** requires a SAME-SESSION upload record + unchanged remote size. Cross-process (fresh batch songs) always upload — correct, not wasteful: each batch-song process uploads once.
  2. **Single build per deploy:** `deploy_pack_bundle` now runs `_ensure_pack_mode_bundles` (modes + variants) BEFORE the first upload — every upload in the deploy carries the same final bytes the catalog encodes. No second build can diverge.
  3. **DEPLOYED-BUNDLE CRC GUARD (the defensive check the user asked for):** post-deploy validation + `--verify-ps4` now pull EVERY deployed pack bundle and verify its actual catalog-scheme CRC equals the manifest/catalog expectation — explicitly naming the crash signature when it fails. This check would have caught the crash BEFORE the game booted.
- **Live repair:** re-deployed all 5 packs' variants + catalog; full `--verify-ps4` with the new guard: all 5 packs ✅ deployed bundle CRC matches catalog → 🎉 PASSED. The user's PS4 is safe to boot.
- **Tests:** 856/856 (5 new: skip-soundness ×3, the crash-number contract [size-equal/crc-different builds must fail], single-build ordering, guard-presence source check). Lint clean.
- **Status:** ✅ crash root-caused from bytes, fixed 3 ways, live state repaired + verified, regression-pinned.
